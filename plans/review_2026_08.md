# Review of cicpy and ciccreator, 2026-08-06

What a read of both trees turned up. The five defects that cannot move a
coordinate are already fixed and pushed (cicpy 490720d). Everything below
either changes generated geometry or changes a golden file, so it is
written down rather than applied. Each entry says what it costs to fix.

## 0. mirrorX stretched rectangles instead of flipping them — FIXED

*ciccreator a6e2eb5.*

`Rect::top()` returns `y1_` but `Rect::setTop()` writes `y2_`, and
`bottom()`/`setBottom()` are crossed the same way. The header comments show
the setters hold the intended convention ("Set the top coordinate (y2)"),
so the getters are the wrong ones. `Rect::mirrorX` used both:

```cpp
setTop(2*ay - top());        // reads y1, writes y2
setBottom(2*ay - bottom());  // reads the y2 just written, writes y1
```

The second line reads back what the first wrote, so y1 stays put and only
y2 moves. The rectangle ends up spanning from its old bottom edge to its
mirrored top edge. For the SUNSAR_NCHDLR source strap, y = 2700..6100
about ay = 8800:

| | y range | height |
| :--- | :--- | ---: |
| correct | 11500..14900 | 3400 |
| produced | 2700..14900 | 12200 |

which swallowed the drain strap and the S port, shorting source to drain.
`mirrorY` is fine — `left()`/`setLeft()` agree on which edge they mean.
Fixed at the call site, not in the getters: `route.cpp` and
`layoutcell.cpp` read `top()`/`bottom()` and expect today's behaviour.

Verified on `sun_sar9b_sky130nm`, regenerated and put through
`make gds cdl lvs drc`:

| | SAR8B LVS | SAR8B DRC | SAR9B DRC |
| :--- | :--- | ---: | ---: |
| committed 2024 design | match uniquely | 30 | 34 |
| regenerated, hook off | 7 mismatch lines | 30 | 34 |
| regenerated, hook on, mirror broken | 12, incl. the short | — | — |
| regenerated, hook on, mirror fixed | **7, the short gone** | 30 | 34 |

- `SUNSAR_NCHDLR` is now an exact mirror of `SUNSAR_NCHDL`, rect for rect.
- klayout XOR against a build with the mirror still broken: **152.7 um2 of
  a 25531 um2 cell, 0.6%**, all inside the mirrored dummies in SARBSSW and
  CDAC7. Nothing else moves.

`Instance::transform` also `mirrorX(0)`s an MX placed instance, but no
generated design in the tree uses MX — only "", "180", "MY", "R90" — so
that path stays dark.

### What is still broken, and is older than any of this

Regenerating sun_sar9b does not pass LVS, and did not before this session
either. With the pre-fix binary the regenerated SAR8B already fails where
the committed 2024 layout matches: capacitor nets in CDAC7 and CAP32C
(`XC1/C2`, `X16ab/C4` and friends have no matching net in the source),
TGPD, and top level pin matching. Two years of tool drift. Untouched here,
and the next thing to pull on.

So `ref.cic` still cannot be regenerated yet: it would freeze those
capacitor mismatches into the golden file.

## 0b. How SAR8B broke: SimpleRect flipped top()/bottom() — FIXED

*ciccreator a34ef45. This closes the "two years of tool drift" from
section 0 — it was one commit, not two years.*

From 2016 to 2024 `top()` returned `y2_`, consistent with `setTop()`,
while a stale comment on the declaration said `//! y1`. `e827239`
(Introduce SimpleRect, 2025-05) reimplemented the getters from the
comment instead of the code, flipping their meaning. Every reader —
mirrorX, route track placement, `cell.cpp`, `layoutcell.cpp` — predates
the rewrite and got the opposite edge from that day on.

Concrete damage in sun_sar9b: every `cut_M2M3_1x2` in the CDAC rail bus
sat exactly one cut height (9200 dbu) too high, leaving the C1A..C16
capacitor rails floating. That is the LVS failure that regeneration
showed.

Fix: restore the getters to match the setters. No post-e827239 code
reads them. Verified:

- `SUNSAR_CDAC7_CV` regenerated vs the committed 2024 GDS: **klayout XOR
  empty, identical on every layer.**
- LVS: SAR8B, CDAC7, CDAC8, CAPT8B, SARBSSW all match uniquely — same
  verdicts as the committed layout. DRC unchanged (SAR8B 30, SAR9B 34).
- SAR9B still fails pin matching on CMP_OP — identically with the
  committed 2024 layout, so that is in the design, not the tool.
- Residual SAR8B whole-cell XOR: 42 um2 (0.16%), the mirrored dummy
  region where VI/VO1 labels sit on swapped straps; pin matching passes.

Consequences for the earlier sections:

- Section 0's "two years of drift" is closed. Regeneration now
  reproduces the taped-out geometry.
- The mirrorX stretch (section 0) was the same flip seen through one
  caller; a6e2eb5 already fixed that call site, a34ef45 fixes the rest.
- `ref.cic` (captured 2025-06, flipped getters live) now differs from
  HEAD by 612 lines, down from 6004. What remains is the reference
  encoding the flip. Regenerate it after deciding sortGraph (1c).
- Every earlier "byte-identical to d423691~1" measurement compared two
  binaries that both carried the flip; consistent, but both were wrong
  against 2024 silicon.

## 1. Zero-argument hooks — the invoke was wrong, but reverted

*Applied as ciccreator 15be668, then reverted in 3cc2978 once LVS showed
what the revived hook produces — see section 0. The original text below
was wrong on the important point and is kept for the record.*

The hooks are not universally dead. `m.invoke(c, Qt::DirectConnection,
Q_ARG(QJsonValue, v))` against a zero-parameter method **succeeds on the
Qt in the CI container**, which quietly drops the extra argument, and
**fails on Qt 6.9**. So `mirrorCenterX` ran for every library ever
generated on Linux, and silently stopped running for anyone building on a
current macOS. The same design file produced different silicon depending
on the machine.

`Design::runMethod` asking `m.parameterCount()` is the right call in
isolation, and on the CI container it is measurably a no-op: identical
output, since that Qt was already running the hook. But what the hook then
does is broken (section 0), so the change is reverted and the defect to
chase is `Cell::mirrorX`, not the invoke.

## 1b. The original text, which had it backwards

`Design::runMethod` (`cic-core/src/core/design.cpp:597`) always passes one
argument:

```cpp
m.invoke(c, Qt::DirectConnection, Q_ARG(QJsonValue, v));
```

`Cell::mirrorCenterX()` and `Cell::mirrorCenterY()` are the only two
`Q_INVOKABLE` methods that take no parameters, and Qt refuses the call:

```
QMetaMethod::invoke: cannot convert formal parameter 0 from QJsonValue
in call to cIcCore::Cell::mirrorCenterY()
```

That line is printed by `make test` in `tests/sar` today. The design files
write the hook as `"afterPaint" : { "mirrorCenterX" : 0 }`, and there are
22 such entries across 14 libraries — `dmos_sky130nm_core.json` in
sun_sar9b, sun_pll, sun_tr, sun_trb, cnr_nssar, jnw_tr, algic_stdlib,
lelo_sar9b, lelo_tr and the two examples. None of them has ever run.
`ciccreator/schema.json` already carries the note
`"mirrorCenterY,help:Not sure if this works"`.

The fix is one branch:

```cpp
if (m.parameterCount() == 0) { m.invoke(c, Qt::DirectConnection); }
```

The cost is that fourteen transistor libraries would start mirroring cells
that have never been mirrored, against silicon that has been taped out.
That is a decision, not a cleanup.

## 1c. SAR::sortGraph is not a strict weak ordering — needs your call

`cic-core/src/cells/sar.cpp:161` sorts the routing graphs with
`std::sort` and a comparator that

- returns false for *every* pair where either side has no SARDIG
  rectangle, so it calls unrelated nodes equal, and
- otherwise compares a single `y2`, which ties constantly.

Ties under `std::sort` are ordered however the standard library likes.
libstdc++ and libc++ disagree, and `SUNSAR_SAR8B_CV` comes out with `D<7>`
and `CN<5>` on swapped M4 tracks depending on the machine. Same geometry,
different nets on it. A comparator that calls a≡b and b≡c while a<c is
also formally undefined behaviour in `std::sort`, not merely unspecified.

`std::stable_sort` fixes it: measured, macOS and the CI container then
produce byte-identical output for the whole design. **But** stable_sort
also changes the tie order relative to libstdc++'s current `std::sort` —
408 lines of the SAR cells move — so it is a layout change on the platform
that generated the existing libraries. Left unapplied for that reason. The
change is one word if you want it.

Until it is decided, `make test` can only be green on one platform at a
time, because the reference is a byte comparison.

## 2. tests/sun_sar9b: reference is stale, regeneration is one command

`make test` in ciccreator is red at HEAD: `diff sar.json ref.json` reports
6004 differing lines.

Bisected by building three revisions:

| revision | differing lines |
| :--- | ---: |
| 357877e, the AGL build fix | 32091 |
| 44a0cb0, before the port fix | 32091 |
| HEAD (99eb68a applied) | 6004 |

So the failure predates all of this month's work, and 99eb68a — restoring
the patterntile fall through — cut the divergence by 80% without closing
it. That is consistent with the cause: `ref.cic` was regenerated on
2025-06-21 (8a0fb59), a month after d423691 broke port geometry on
2025-05-16. The reference file was captured while the bug was live, so it
encodes it.

That was the hypothesis. It is now established, by building the commit
*before* the port bug was introduced:

- `d423691~1` (May 2025, pre-regression) and HEAD produce **byte-identical**
  output, 0 differing lines. So 99eb68a restored the geometry exactly, and
  what HEAD generates today is what the tool generated before the bug.
- `ref.cic` matches neither. It was committed 2025-06-21, inside the
  regression window, and it encodes the broken port geometry.
- It was never validated: the CI paths filter listened only to `**.cpp`,
  `**.h` and `Makefile`, and 8a0fb59 touched only json, yaml and ref.cic,
  so the workflow did not run. The reference has never once been checked
  against the tool. Filter widened in 15be668.

So the reference is stale and will eventually need regenerating. **Not
yet** — see section 0. A regenerated reference today would freeze the
NCHDLR short into the golden file.

A candidate is already generated and sitting next to it, produced in the
CI container from 15be668:

    tests/sun_sar9b/ref_candidate_linux.cic     # untracked

It is byte-identical to what the CI container generates at HEAD. To adopt:

    cd tests/sun_sar9b && mv ref_candidate_linux.cic ref.cic

I did not do that move: overwriting a golden reference is your call, not
something to do while you are asleep, and the sort in 1c means the result
is only green on Linux until that is decided.

Note that 8a0fb59 does not build on a current SDK (the AGL link error,
fixed later by 357877e), so testing that revision needs the sed from
`make strip_agl` applied by hand.

## 3. Route rings take their vertical spacing from the horizontal grid

Three sites in `cicpy/src/cicpy/core/layoutcell.py`:

```python
xgrid = Rules.getInstance().get("ROUTE","horizontalgrid")*spacemult + mw
ygrid = Rules.getInstance().get("ROUTE","horizontalgrid")*spacemult + mw
```

`addRouteRingOnRect` (1213), `addPowerRing` (1654) and `addRouteRing`
(1671). In sky130A `horizontalgrid` is 30 and `verticalgrid` is 40, so
every ring is spaced 25% tighter vertically than the rule intends.

The C++ has the mirror image of the same copy-paste — `LayoutCell::addGuard`
(`layoutcell.cpp:684`) takes both `xenc` and `yenc` from `verticalgrid`.
One of the two is wrong in each tool and they are wrong in opposite
directions.

Fixing it moves every ring and guard in every cell that uses them.

There is a second trap sitting behind it. Both tools call

```
RouteRing(layer, name, rect, location, ygrid, xgrid, metalwidth)
```

against a constructor declared `(..., int xgrid, int ygrid, int width)`.
The two arguments are swapped at the call site, in cicpy and in C++ alike.
It is invisible today only because the two values are equal. Whoever fixes
the paragraph above has to fix this in the same commit or the ring will
come out spaced correctly on the wrong axis.

## 4. Cut enclosure tests one rule and reads another

`cicpy/src/cicpy/core/cut.py:68` and `:107`, and identically
`cic-core/src/core/cut.cpp:36` and `:70`:

```python
encRule = l.next + "encOpposite"      # e.g. "COencOpposite"
encThis = l.next + "enclosure"        # e.g. "COenclosure"
if rules.hasRule(l.name, encRule):    # asks about encOpposite
    enclosure = rules.get(l.name, encThis)   # fetches encThis
```

The guard asks whether the *opposite* rule exists and then reads the
*this* rule, which is a different key. In sky130A the layer `OD` has
`COencOpposite` and plain `enclosure` but no `COenclosure`, so the branch
is taken, the lookup fails, and the bare `except` — now `except Exception`
— hands back an enclosure of 0. The plain `enclosure` value that was meant
to be used is right there and never read.

cicpy reproduces the C++ faithfully, and the C++ carries a matching TODO
four lines above: "OD -> M1 contact is not generated correctly, should fix
at some point". So this is a known-shaped bug with a name now.

Fixing it means testing `hasRule(l.name, encThis)`, which changes the
enclosure on OD/CO contacts, which changes every via that has ever been
generated. Same class of decision as item 1.

## 5. Smaller things, no action needed

- `Design::runIfObjectCanMethods` (`design.cpp:667`) slices the plural
  form with `method_key.left(key.length()-1)` — the length of the
  untranslated key against the translated string. Harmless today because
  the only translation is `type` to `mosType`, and `mos` is not a method.
- `MagicPrinter` writes `timestamp` from today's date, so every `.mag`
  churns once a day even when the geometry is unchanged. It makes
  "regenerate and diff" noisier than it needs to be; grep out `^timestamp`
  when comparing.
- `cicpy/core/rect.py:85 snap()` hardcodes a 5 unit grid and is dead code.
  If it ever comes back it should ask `Rules` (see `core/gridcheck.py`),
  and it truncates toward zero, which rounds negative coordinates the
  wrong way.
- pyflakes reports roughly forty unused imports and locals across
  `src/`. Noise, but it is what hid the two NameErrors that were fixed.

## What was checked and is fine

- ciccreator compiles clean under `-Wall -Wextra`; the only warnings are
  Qt's own deprecations of `QJsonValue::type` and `create` in `design.cpp`.
- No mutable default arguments, no identity comparisons against literals,
  no swallowed `except: pass` in a path that decides geometry.
- cicpy `make test` passes, and the seven cells regenerate byte identical.
